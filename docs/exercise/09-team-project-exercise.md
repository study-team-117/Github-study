# 09 チーム開発総合演習｜2人でREADMEを改善する

[← 09章の本編](../09-team-project.md) ｜ [目次に戻る](../../README.md#目次)

> **演習の目安**　基本15〜20分 ｜ 応用15〜20分 ｜ 発展15〜20分
>
> 事前準備を終えてからの目安です。ペアで取り組みます。発展は任意です。

## 事前準備

- 片方がREADME付きの練習専用リポジトリを作成し、Issuesを有効にします。READMEの先頭の見出し直後に「このリポジトリは練習用です。」と書き、GitHubの `main` に反映します。発展演習ではこの行を使います。
- 相手を共同作業者に招待し、招待を承諾してから2人ともcloneします。
- GitHubで既定ブランチが `main` であることと、双方が作業ブランチをpushし、PRをレビューできることを確認します。マージは権限のある人が担当します。

## 基本演習

### 課題1：Issueを作り、1件目のPRをマージする

1. 「使い方を追加」「困ったときの確認手順を追加」のIssueを1件ずつ作り、担当と完了条件を書きます。
2. Aさんは更新済みの `main` から `docs/add-usage` を作り、READMEに「使い方」の見出しと、この教材で練習できる操作を2つ追加します。
3. 差分を確認してコミット・pushし、`main` 向けのPRを作ります。説明欄に確認方法と `Closes #1` のような記述を加えます。`1` は担当Issueの番号に置き換えます。
4. Bさんは差分とMarkdownの表示を確認し、確認したことをPRに残します。担当者がマージし、AさんとBさんは手元の `main` を更新します。

**完了チェック**

- [ ] `main` に「使い方」が表示され、対応するIssueが閉じた。

## 応用演習

### 課題2：役割を交代し、レビューの指摘に対応する

1. Bさんは更新済みの `main` から `docs/add-troubleshooting` を作ります。READMEに「困ったとき」を追加し、たとえば「まず `git status` を確認する」と書いてPRを出します。対応するIssueを `Closes #2` のように指定します。
2. Aさんは、初めて読む人にも「結果のどこを見て、次に何をするか」が分かるかを確認し、改善案を1つ伝えます。差分に秘密情報や対象外のファイルが含まれていないことも確認します。
3. Bさんは同じブランチで文章を修正してpushし、PRのコメントに修正点を書きます。
4. Aさんが再確認したらマージし、GitHubの `main` に2つの節があることを確認します。

**完了チェック**

- [ ] 2件目のIssueが閉じ、同じPRに「指摘 → 修正 → 再確認」の記録が残った。

## 発展演習

### 競合を解消し、2人の意図を取り込む

1. どちらも新しい `main` を取得し、同じコミットから別々の作業ブランチを作ります。AさんはREADME冒頭の「このリポジトリは練習用です。」をGitの基本操作を紹介する文に、Bさんは同じ1行をPRレビューを紹介する文に置き換えます。2人とも先にコミットして別々の作業ブランチをpushし、`main` 向けのPRを作ります。
2. AさんのPRを先にマージします。BさんはGitHubで自分のPRに競合が出ていることを確認します。
3. Bさんは自分の作業ブランチで `git fetch origin` の後に `git merge origin/main` を実行します。[04章](../04-troubleshooting.md)を参照して、両方の意図が伝わる1行にまとめます。
4. 競合を解消してpushし、どうまとめたかをPRに書きます。Aさんが差分を再確認してからマージします。Actionsを設定済みの場合は **Checks** が成功していることも確認します。

**完了チェック**

- [ ] `main` のREADME冒頭に両方の意図が反映され、既存の2つの節も読める。
- [ ] 競合の解消方針がPRに残っている。
