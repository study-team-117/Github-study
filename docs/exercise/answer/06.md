以下は一例です。ブランチ名やファイル名は配布されたものに合わせ、コミットID・Issue番号は実際に表示された値を使います。

## 基本演習

### 完了を判断できるIssueを書く

**使用環境**　GitHubのIssuesをブラウザで操作します。PCへのクローンやターミナル操作は不要です。

**選んだ理由**　Issueを引き継ぐ人が完了を判断できるように、対象・依頼内容・完了条件を書き分けます。

GitHubの **Issues → New issue** で、タイトルを「READMEに開催案内を追加」とします。本文には「READMEにA教室と受付15時を掲載する。READMEを開いて両方読めれば完了」と書きます。

**確認**　作成したIssueを読み、担当者が対象ファイルと確認する内容を判断できるか確かめます。

## 応用演習

### IssueとPRを関連付け、取り込みを確認する

**使用環境**　準備のファイル編集とGit操作はPCのエディターとターミナルを使います。Issue・PR・Actionsの確認、レビューとマージはGitHubのブラウザで行います。

**選んだ理由**　PRとIssueを結び付けると、依頼をどの差分が満たしたかを追跡でき、既定ブランチへのマージで対応完了を記録できます。

`main` 向けのPRの説明に `Closes #実際のIssue番号` を書きます。レビュー担当は **Files changed** でA教室と15時の記載を、**Checks** で結果を確認します。

**確認**　権限のある人が既定ブランチの `main` に取り込みます。GitHubのREADMEで案内が読め、Issueが **Closed** でPRとの関係が分かることを確認します。

## 発展演習

### 仕様・差分・ログからチェック失敗を調べる

**使用環境**　Issue・PR・ActionsのログはGitHubのブラウザで確認し、ファイルの修正と記録はPCで行います。原因調査にはエディターの差分表示や、ターミナルでのローカルテストも使えます。

**選んだ理由**　Issueが仕様の根拠です。空文字に対する期待値が仕様どおりなら、テストを変えて成功に見せると誤りが残ります。ログと差分で実装を調べます。

失敗した `test_empty_input` では期待値「未入力」に対し実際の値が空文字です。PC上のエディターで `display.py` を開き、`display_label` の戻り値を次のようにします。

```python
def display_label(value):
    return value if value else "未入力"
```

**確認**　Python 3で `python -m unittest -v` を実行し、通常入力と空欄の2件が成功することを確認してからターミナルから同じ作業ブランチに反映します。ブラウザでPRを開き、「仕様と異なり空文字をそのまま返していた。戻り値を修正し2件を確認した」と記録します。GitHubのチェックが待機中なら、ローカルでの成功とGitHubでの未確認を区別します。
