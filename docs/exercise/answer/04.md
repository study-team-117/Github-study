# 04 エラー・コンフリクト対処｜ミニ演習 回答例・解説

[← 演習に戻る](../04-troubleshooting-exercise.md) ｜ [← 04章の本編](../../04-troubleshooting.md) ｜ [目次に戻る](../../../README.md#目次)

以下は一例です。ブランチ名やファイル名は配布されたものに合わせ、コミットID・Issue番号は実際に表示された値を使います。

## 演習1：編集を残したままコミット対象から外す

**使用環境**　PCのターミナルでGitの状態を確認・操作し、編集内容はエディターで確認します。GitHubへの接続は不要です。

**選んだ理由**　ステージから外す操作を選ぶと、作業中のファイルを保存したまま、次のコミットから除外できます。

次の順で、対象を外す前後の状態を確認します。

```bash
git status
git restore --staged practice.md
git diff --staged
git diff -- practice.md
```

**確認**　`git diff --staged` には追記がなく、`git diff -- practice.md` には未記録の追記が残ります。

## 演習2：両方の意図が残るように競合を解消する

**使用環境**　PCのターミナルで統合の状態を管理します。競合箇所の編集には、使い慣れたエディターやその競合解消画面を使えます。

**選んだ理由**　両ブランチを統合すると、同じ行の内容は自分で決められ、ブランチの別ファイルも同時に取り込めます。

`main` から統合を始めます。競合したら、READMEの競合箇所を「確認方法：ターミナルで状態を見て、VSCodeで差分を見る」の1行にして保存します。

```bash
git switch main
git merge practice/conflict
# 競合したら上の説明に沿って README.md を編集
git status
git add README.md
git diff --staged --check
# 出力がないことを確認してから続ける
git merge --continue
git status
```

`--check` は、ステージ済みの差分に競合の印や余分な空白などが追加されていないか確認します。指摘があれば、編集して再度ステージします。

**確認**　READMEに競合の印がなく、`branch-note.md` もあることを確かめます。最終的に未解決の競合がなく、統合のコミットを確認できれば完了です。

## 演習3：誤変更を取り消し、取り込み待ちのPRを整える

**使用環境**　変更とGit操作はPCで行い、PRとレビューにはGitHubのブラウザを使います。競合の内容を説明できれば、エディターの競合解消画面も利用できます。

**選んだ理由**　誤った締切はすでに共有されているため、該当コミットの逆の変更を新しく記録します。PRの競合は未取り込みの案内文の問題なので、先に締切の訂正を共有してから、作業用ブランチで別に解決します。

`git log --oneline -- deadline.md` で締切ファイルの履歴に絞り、`git show <コミットID>` で取り消す変更を確認します。IDを置き換え、次のように進めます。`--ff-only` は履歴の分岐時に止まり、`--no-edit` は取り消しコミットのメッセージを既定のまま使います。

```bash
git switch main
git pull --ff-only
git switch -c fix/deadline
git revert --no-edit BAD_COMMIT_ID
git push -u origin fix/deadline
```

訂正PRをレビューして `main` に取り込んだあと、別件PRを更新します。

```bash
git fetch origin
git switch practice/announcements
git merge origin/main
```

競合したREADMEに「質問は掲示板へ。急ぎの場合は担当者へ連絡してください。」を残します。保存したら、次の操作を行います。

```bash
git add README.md
git diff --staged --check
# 出力がないことを確認してから続ける
git merge --continue
git push -u origin practice/announcements
```

**確認**　ペアの相手が最新版の `main` で締切と連絡先を確認します。別件PRでは、READMEに両方の案内があり、競合が解消されたことを確かめます。
