# 08 Git・GitHubのセキュリティ｜ケーススタディの解説

[← 演習に戻る](../08-security-exercise.md) ｜ [← 08章の本編](../../08-security.md) ｜ [目次に戻る](../../../README.md#目次)

**必須の対策**は、このケースの条件で安全を確保するために必要な対応です。**推奨する対策**と**その他の対策例**は、目的、チームの権限、使用できる機能に応じて選べます。着目したリスクと、対策後に何を確かめるかを説明できることを重視します。

## 基本演習

### 共有前にファイルと権限を見直す

| 観点 | 判断の例 |
|---|---|
| 想定されるリスク | `.env` のキーは外部サービスにアクセスできる。実データ入りのSQLiteファイルには、共有目的に不要な氏名と連絡先がある。 |
| 必須の対策 | 共有前に `.env` と `participants.sqlite` を対象から外し、送る差分に値や個人情報がないことを確かめる。チーム外の閲覧者をメンターに限定し、書き込み権限を付けない。 |
| 推奨する対策 | Privateの練習リポジトリで、組織のリポジトリならメンターに `Read` を割り当てる。`.gitignore` に対象の除外ルールを共有し、設定項目はダミー値の `.env.example` で伝える。 |
| 理由と優先順位 | まず秘密情報と実データが送られない状態にする。次に閲覧範囲と権限を確認する。スキーマとダミーデータがあれば、実データを出さずに構成と動作を説明できる。 |
| その他の対策例 | 共有が許可されたコード・データだけの資料を作り、所属先が認めた閲覧専用の方法で渡す。 |
| 不適切な対応 | 「Privateだからキーを入れてもよい」と判断すると、共同作業者や連携ツールへ値が渡り得る。閲覧のために `Write` を付けると、必要のない権限まで与えることになる。 |

## 応用演習

### APIキーの漏えいに対応する

| 観点 | 判断の例 |
|---|---|
| 想定されるリスク | 最新版で消えていても過去のコミットや取得済みのコピーに値が残る。有効なキーは権限の範囲内で使われ、データの読み取りや課金につながるおそれがある。 |
| 必須の対策 | **発行元で旧キーをすぐ失効**させる。権限がなければ担当者に直ちに依頼する。値を再共有せず管理者に連絡し、キーの権限、発覚時刻、リポジトリ・ファイル・コミット、失効状況を伝える。発行元の記録で影響を確認する。 |
| 推奨する対策 | アプリに必要なら新しいキーへ切り替え、利用権限を絞る。発覚前後の利用ログ・課金、PRやログなどの共有範囲を調べる。設定例、除外ルール、差分確認を見直す。 |
| 理由と優先順位 | 失効を最優先にし、連絡も早期に行う。失効確認後に必要な再発行を進め、利用履歴で被害の有無と影響を確認する。最終的に旧キーが無効で、必要なアプリが正常に動くことを確認する。 |
| その他の対策例 | 必要に応じて管理者と履歴整理を計画する。対象パターンが対応していればSecret scanningやPush protectionを使い、レビューと組み合わせる。 |
| 不適切な対応 | ファイルの削除や公開範囲の変更だけで終えると、過去の値やコピーが残る。失効を後回しにして履歴を書き換えると、有効なキーが残る時間が延び、チームの作業にも影響する。 |

## 発展演習

### チームでAI開発支援ツールを使うルールを決める

| 観点 | 判断の例 |
|---|---|
| 想定されるリスク | 本番ログの送信で情報が外部へ渡る。広い書き込みや本番アクセスがあると誤操作の影響が広がる。外部資料に紛れた指示や、生成コードと新しい依存関係が意図しない動作を引き起こす可能性がある。 |
| 必須の対策 | 秘密情報や個人情報を送らず、許可されたデータと作業範囲だけを使う。本番へのアクセスや不要な書き込み・外部送信を許可しない。資料の指示による操作はそのまま実行せず、人がコマンドと対象を確認する。マージ前に人が権限、依存関係、差分を確認し、必要なテストを行う。 |
| 推奨する対策 | 作業担当が伏せ字やダミーデータを用意して限定したフォルダで調査する。レビュー担当が依存関係と差分、テスト結果を見て、マージ担当が合意した条件を確認する。確認結果をPRに残す。 |
| 理由と優先順位 | まず外部送信と本番への影響を防ぐ。次に、許可するファイルとコマンドを決めてから作業を始める。最後に、人のレビューとテストを行い、無理なく運用できる自動チェックを選ぶ。 |
| その他の対策例 | 読み取り中心の調査なら、専用の作業コピーとダミーログで提案を受ける。書き込みが必要な場合は対象フォルダを絞り、追加の権限が必要な操作だけ承認を求める。依存更新はDependabotの通知も利用できる。 |
| 不適切な対応 | CIの成功だけでマージすると、テストしていない権限の抜けや不要な外部依存を見逃す。ツールの出力や資料の文章だけで外部送信を決めると、チームの許可範囲を超え得る。 |
