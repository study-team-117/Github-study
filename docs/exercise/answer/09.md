# 09 チーム開発総合演習｜回答例・解説

[← 演習に戻る](../09-team-project-exercise.md) ｜ [← 09章の本編](../../09-team-project.md) ｜ [目次に戻る](../../../README.md#目次)

Issue番号とPR番号は練習リポジトリで表示された実際の番号に置き換えます。

## 基本演習

### 課題1：Issueを作り、1件目のPRをマージする

Issue「使い方を追加」の完了条件は「READMEに『使い方』があり、練習できる操作を2つ説明している」とします。担当はAさんとします。もう一方のIssueはBさんを担当にして、完了条件を「困ったときの最初の確認手順をREADMEから読める」とします。READMEには、たとえば次のように書けます。

```markdown
## 使い方

- 作業ブランチを作り、変更をコミットする。
- Pull Requestを作り、GitHubで差分を確認する。
```

Issueが `#1` なら、PRの本文には「READMEに使い方を追加しました。Files changedで追記範囲と表示を確認しました」と書き、別の行に `Closes #1` を記載します。Bさんは「見出しと操作例があり、READMEの表示を確認できました」とレビューします。マージ後にIssueの **Closed** と、`main` のREADMEを確認します。

## 応用演習

### 課題2：役割を交代し、レビューの指摘に対応する

レビューの例は「`git status` の結果のうち、どこを見ればよいか1行足すと、初めて読む人も進めやすいです」です。Bさんは、たとえばREADMEを次のように修正します。

```markdown
## 困ったとき

`git status` を実行し、現在のブランチ名と変更されたファイルを確認します。
作業する予定のブランチと違っていたら、変更を加える前にブランチを確認してください。
```

同じブランチにpushし、PRで「見るべき箇所として、ブランチ名と変更ファイルを追記しました」と返信します。Aさんは更新された差分を再確認します。マージ後、2つの見出しが表示され、2件目のIssueが閉じていれば完了です。

## 発展演習

### 競合を解消し、2人の意図を取り込む

Bさんは自分の作業ブランチにいることと未コミットの変更がないことを確認し、次を実行します。

```bash
git fetch origin
git merge origin/main
git status
```

READMEの競合した部分を読み、「このリポジトリではGitの基本操作とPull Requestのレビューを練習します。」の1行にまとめます。競合マーカーが残っていないことを確認してから、次のコマンドを順に実行します。

```bash
git add README.md
git diff --cached
git merge --continue
git push
```

PRには「冒頭の1行が競合したため、Gitの基本操作とPRレビューの両方を紹介する文にまとめました」と記載します。AさんはGitHub上でもう一度差分を確認し、マージ後に `main` の表示を確認します。
